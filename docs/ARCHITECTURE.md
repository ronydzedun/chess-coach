# Architecture

Chess Coach is a Rust 2024 workspace with four crates:

```text
desktop ──> chess-core
   │
   ├──────> engine
   └──────> chess-library (SQLite)
```

`desktop` provides the `chess-coach` binary and the `iced` 0.14 interface. It uses the `tiny-skia` software renderer with Wayland and X11 support. A custom board widget paints squares, SVG pieces and highlights directly; rank/file labels participate in normal Iced layout. Mouse/touch press and motion only update local widget state and request redraws, including the first selection of a piece. The committed app selection changes on release. Legal destinations are cached per press or committed selection. The moving piece preserves its grab offset and follows from the first pixel; a five-pixel threshold distinguishes clicks from drops.

Markers retain fixed render slots, becoming transparent when inactive. The source SVG also retains its slot with zero opacity during a gesture; only the moving preview is appended. This avoids shifting the software renderer’s primitive lists and invalidating unrelated areas when a piece is first selected. Dev builds optimize the three raster-renderer crates while application code retains ordinary debug settings.

Release messages carry the position revision and pointer epoch. The app rejects stale clicks/drops before applying the existing `chess-core` validation and promotion flow. Escape, flip, modal opening and position changes invalidate the gesture. Window exit, resize and focus loss clear the local preview and restore the committed selection. One touch finger is tracked and released on cancellation. Ordered event coordinates avoid Iced’s shared cursor snapshot for a batch; clicks remain interpreted in app message order. Design references: [Qt drag hot spots](https://doc.qt.io/qt-6/qtwidgets-draganddrop-draggableicons-example.html) and [Chessground’s separate motion/drop paths](https://github.com/lichess-org/chessground/blob/master/src/drag.ts); the Rust implementation is original.

`chess-core` wraps `shakmaty` 0.30.2 for standard chess rules, FEN, UCI move parsing, and SAN generation. It owns the position, undo snapshots, move history, and a revision counter. A move or FEN load is validated before state changes, so rejected input leaves the position untouched. Loading valid FEN starts a fresh local history. Review lines can be loaded as independent validated histories while preserving the revision sequence used to reject stale analysis.

PGN import uses `pgn-reader` 0.29.1 and validates the main line against `shakmaty`. The parser accepts standard-chess games, UTF-8 (with an optional BOM), comments, NAGs, and `SetUp`/`FEN` tags. It rejects malformed structure, illegal or unsupported SAN, unsupported variants, invalid FEN, and missing game results. An import is committed only when every game parses successfully. Input is limited to 8 MiB, 256 games, 2,048 plies per game, and 50,000 plies total. Variations are not retained for review and comments are not shown.

`engine` is a local UCI process service. Its worker owns process I/O and handshake waits, sends position and depth/time analysis requests, parses one principal variation in UCI coordinate notation, and reports centipawn or mate scores from White's perspective. Events carry request IDs and stale requests are cancelled. The service bounds queued events and cleans up its child process. A saved explicit engine path takes priority. Otherwise the desktop interface discovers Stockfish using `STOCKFISH_EXECUTABLE`, then `PATH`, then `/usr/games/stockfish`. No engine binary is bundled. Automatic analysis is ON at every launch and can be toggled ON/OFF for the current session. It begins at startup and is debounced by 300 ms after position, FEN, import, and review-navigation changes. The time limit defaults to 1000 ms and accepts 1–300000 ms; depth accepts 1–128 and retains a 60-second safety deadline. Changing engine path or limit restarts pending automatic analysis. Engine errors do not create a retry loop.

The `chess-library` crate owns the SQLite data model. A dedicated database worker owns its connection so disk access never runs on the UI thread. Startup loads stored imports, completed analyses and the active review game/cursor. Exact PGN text is retained with game IDs; importing identical text reuses the existing import. Source PGN and original lines remain unchanged while navigation and exploratory moves use an in-memory working branch. The active original game and cursor are restored on restart, and pending main-line analysis resumes automatically. Working branches and graph previews are presentation state and are not persisted. There is no PGN export, network service, or LLM integration.

The library database is `ProjectDirs::from("org", "chess-coach", "chess-coach").data_local_dir()/library.sqlite3` (on Linux, normally `~/.local/share/chess-coach/library.sqlite3`, respecting `XDG_DATA_HOME`). SQLite runs in WAL mode and may have adjacent `-wal` and `-shm` files. Close the application before manually copying the database for backup. Schema version checks reject unrecognized, newer and corrupt databases with a visible error; startup does not automatically delete, replace or destructively migrate them.

## Process and UI lifecycle

The desktop owns the active `Game`, the retained imported source, and the selected original game. A 50 ms Iced/Tokio subscription drains engine events; no engine I/O runs on the GUI thread. File reading and PGN parsing run off the GUI thread. A search captures both a unique request ID and the game's revision. Every position change cancels analysis, and events must match both before they can update the visible evaluation. Moves, review navigation, successful FEN loads, undo and reset invalidate analysis; failed or cancelled imports preserve the current board. Flipping only changes presentation. The board's adjacent vertical evaluation bar is white-relative: centipawns map through a bounded tanh scale with 400 cp as its scale factor, so the bar is not a win-probability estimate. Unknown scores are neutral, mate scores saturate at either end, and M0 marks the winner.

Undo in review is non-destructive: it moves the cursor backward while retaining the forward working line. Advancing restores those moves. A new move after going backward truncates only the future of the working line; the retained imported original remains available through reload or game selection. Left/Right navigate one ply and Home/End jump to the line boundaries when a text editor does not own keyboard focus. The native file picker uses `rfd` 0.17.2; on Linux it uses XDG Desktop Portal with a `zenity` fallback, and on Windows/macOS it uses native dialogs.

The engine service has one worker, one latest-request slot and one cached session keyed by executable path and resource options. Startup sends `uci`, reads `uciok` plus the advertised Threads/Hash spin limits, applies Threads before Hash and waits for `readyok`. Both values are validated before either option is changed. Generic UCI engines without these options remain usable with the legacy 1-thread/16-MiB values; non-default unsupported settings report an error.

Related positions reuse the ready process and its transposition table. Searches still have unique tokens and position revisions. Cancellation sends `stop`, consumes the old `bestmove`, then waits for an `isready`/`readyok` barrier before reusing the session. Old results are never assigned to the next position. A one-second stop/readiness deadline drops an unresponsive process. Handshake waits retain a five-second deadline. Changing path or resources, starting a new game, successfully loading FEN, or selecting/reloading an imported game calls `reset`: it cancels analysis and asynchronously releases the previous process and allocation. Idle process exits are detected and the next search creates a new session.

`stop` invalidates the generation immediately and retains a healthy idle process/cache. Idle output is drained in bounded batches. `Drop` sends stop/quit, allows a short grace period, then kills and reaps an unresponsive child. The bounded reader uses Unix polling or Windows `PeekNamedPipe`, so inherited stdout does not prevent shutdown. Required Threads/Hash advertisements and terminal protocol messages survive queue pressure. Search, line, PV and queue sizes have bounds. Depth searches have a 60-second safety deadline; time searches accept up to five minutes.

`Engine::drop` joins its worker and reader after cleanup. There is no detached child service. The engine is optional; if no executable is found, the board remains usable and automatic analysis reports the issue without retrying. Appearance preferences are persisted separately in `appearance.json` via `directories::ProjectDirs::from("org", "chess-coach", "chess-coach")`. This resolves to `$XDG_CONFIG_HOME/chess-coach` (normally `~/.config/chess-coach`) on Linux, `~/Library/Application Support/org.chess-coach.chess-coach` on macOS, and `%APPDATA%\chess-coach\chess-coach\config` on Windows. The JSON file is limited to 64 KiB and supports at most 32 custom palettes with unique names of at most 40 characters and distinct light/dark `#RRGGBB` colors. Saves use a same-directory temporary file and atomic replacement. Invalid settings fall back to defaults and the error is shown in the footer and the Appearance section of Settings. The saved appearance settings also include time/depth analysis mode and its limit. Three bundled SVG sets are Merida, Celtic and RhosGFX; four built-in palettes are Classic, Green, Blue and Slate. Custom palette colors and the selected piece set/palette are saved. DejaVu Sans is used by the UI; chess pieces are SVG artwork, not Unicode glyphs. Persistence for training and a coach remain future work.


## Settings dialog

The Settings dialog is a modal Iced overlay with Engine and Appearance sections. Pointer events and board shortcuts are blocked while it is open; engine polling continues. Engine path, CPU threads and Hash edits are a draft until Apply. An invalid path or failed save preserves the active engine and the previous configuration. Apply saves first, then changes the engine, cancelling stale analysis if necessary. Closing, Cancel, Escape and backdrop clicks discard the path draft. Appearance changes still apply and save immediately. `engine_path` is an optional field in the existing `appearance.json`; older appearance files remain compatible. A saved custom path overrides discovery. Clearing it restores discovery through `STOCKFISH_EXECUTABLE`, PATH and `/usr/games/stockfish`.

Legal-move markers are filled circles for empty destinations and softly tinted squares for captures. Hover and check indications use background shading; no square borders are drawn.

Resource settings are `engine_threads` (1–1024) and `engine_hash_mib` (1–4096) in the same JSON file. Missing fields default to half the available logical CPU threads, clamped to 1–8, and 256 MiB Hash. The configured engine may impose narrower bounds, checked against its UCI advertisements. Applying resource changes while automatic analysis is OFF releases the old idle session without starting a new search. Total engine memory includes NNUE networks and other allocations in addition to Hash. Settings changes and Escape in a focused input do not leak board shortcuts or partial values to active analysis.


## Completed analysis cache

The desktop keeps a 256-entry in-memory LRU cache for general analysis, independent of the engine's transposition table. Imported-game final analyses are persisted in SQLite by game, position ply and configuration signature. The signature includes the executable path and captured file identity (size and modification time), exact time/depth limit and full position history, including root FEN and moves. It is a metadata fingerprint, not a cryptographic hash; cached analyses are tied to local paths and are not automatically portable between machines. Threads/Hash remain execution options and do not invalidate completed results. Only a matching natural final `BestMove` result is stored; quick previews, errors, cancellation, stale events and watchdog `Incomplete` results are not saved.

Position changes synchronously look up the in-memory cache and loaded library results. Outside imported-game review they invalidate the active foreground request; during review a compatible in-flight search is retained as background work with its accumulated Info. Hits restore evaluation/depth/PV/best move, mark the status Cached analysis and leave no scheduled or active foreground search; useful background game analysis may continue. This also works with automatic analysis disabled. Misses follow the existing debounce when analysis is enabled. Terminal events clear active identity, so late events cannot overwrite a restored result. Reanalyze explicitly bypasses lookup; a failed refresh retains any previous completed entry. The general LRU disappears on exit; imported-game final analyses remain in the library.

## Imported game analysis queue

`desktop::analysis_plan` builds a bounded snapshot of every position in the selected imported main line, including its root (at most 2049 positions). When the requested limit is greater than 200 ms or depth 8, analysis uses two passes: the current position gets priority, then remaining positions receive a quick 200 ms/depth-8 pass. A second pass analyzes all positions at the requested limit, prioritizing positions with large score swings or mate changes from their preview. The graph may show quick previews while work continues; final results replace them. Progress counts two work units per position in two-pass mode; final completion counts positions while quick-pass progress is reported separately. One shared UCI worker serves foreground and background requests. Navigation preserves an in-flight search until it finishes; after completion, the most recently opened uncached position has priority.

The selected game's results remain separate from the general LRU, so a long game's analysis cannot evict itself. Cache lookup consults loaded library results before the 256-entry LRU. Engine path or time/depth criterion changes create a new result signature and queue; Threads/Hash changes retain completed results and update options for pending searches. Game switches, New and successful FEN loads cancel active requests. OFF stops active work and pauses pending positions; ON resumes. Engine errors pause without automatic retry loops; watchdog-incomplete positions are skipped with a visible count, and an explicit resume may retry them. Exploration of a working-line branch retains the original imported game's queue. Completed exact analyses and active game/cursor persist; uncompleted work resumes after restart.

All occupied squares support visual dragging. Only the side to move generates hints or submits a drop; opponent drags clear the local preview on release without sending a move or changing committed selection.

## Board move animation

`desktop::board_animation` holds presentation-only 140 ms cubic ease-out flights. A successful move or adjacent review seek emits a revision-tagged transition from a small 64-square snapshot; chess state and engine scheduling commit immediately. Castling includes a rook flight, while promotion shows the moving pawn before the final promoted piece. Captures update with the committed position. Undo reverses the same transition; large seeks, imports, New and FEN loads do not create flights.

The board widget starts each revision once and schedules redraws at 16 ms intervals only while flights remain. Background engine polling cannot restart them. Rapid navigation preserves unrelated flights and reversals start from the currently displayed position. Static destination SVG slots are kept transparent until the flight ends. Mouse/touch press interrupts animation before direct dragging. A remembered drop suppresses replay of the dragged piece, including after a promotion choice; a castling rook can still glide. Flip, modal changes, resize and focus loss clear transient motion. Coordinates are stored in board units and mapped for either orientation. Animation never blocks input or delays a move.

## Imported game report

The Report tab renders the selected imported main line's completed scores as a responsive native Iced widget. The SVG geometry is generated locally with no downloaded chart assets. Values are White-relative pawn units, clamped at ±10; mate scores saturate, including side-aware mate zero. Missing/incomplete scores remain gaps. Each index is a half-move, including the root at index zero. A marker follows the current main-line position and disappears on a working branch. Clicking restores that original position without replacing the retained analysis queue. The graph updates as searches finish and does not start extra engine work merely by opening the tab.
